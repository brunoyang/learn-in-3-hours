# 事实核查规范

## 为什么要单独一轮核查

模型对快速演进领域的记忆偏旧，训练数据里旧版本的资料往往比新版本多得多。最常出错的两类说法是：

- **默认值和参数**：它们会悄悄改变，旧值读起来依然合理。
- **绝对否定**（“X 不支持 Y”“只能……”）：曾经是真的，后来某个版本加上了。

真实案例：一份公开的 AI 生成 Kafka 课程声明“以 4.x 为准”，却写了“Follower 不对外提供读”（2.4 版起已支持从 Follower 读取，见 KIP-392），以及“linger.ms 默认 0”（4.0 起改为 5ms，见 KIP-1030）。第一条还被写进了类比边界、复述题要点和类比库，也就是说，学习者会被反复训练去记住一条错误。学习者没有能力发现这类错误，发现它是备课人的责任。

## 1. 定基线

- 写下截至日期（今天）和版本（如适用），放进 `course.json` 的 `baseline` 字段。
- 查文档时查**对应版本**的文档（很多项目的文档 URL 里带版本号），不要随手用搜索结果里最先出现的旧版。
- 版本类主题：读最近 2–3 个大版本的 release notes、upgrade/migration guide 和 changelog，在 research.md 里列出“最近改了什么”。升级指南是发现默认值变更、功能移除的最佳单一来源。
- 非软件的时效主题（利率、税率、法规、统计数据、医疗指南）同理：找发布机构的最新版本，并记下发布日期。

## 2. sources.json

```json
{"id": "S3", "title": "Producer Configs", "url": "https://kafka.apache.org/41/configuration/producer-configs/",
 "publisher": "Apache Software Foundation", "date": "4.1 docs", "tier": 1}
```

- `tier` 分四层。1：一手资料，即官方文档、规范/标准、法规原文、监管机构、原始论文、统计机构。2：教科书、权威百科、参考书。3：名校公开课、专家署名的深度文章。4：其他。第 4 层不能作为任何一条说法的唯一依据。
- `date` 写发布日期、文档版本或“accessed YYYY-MM”。学习者要靠它判断资料新不新。
- 至少 3 个来源、至少 2 个互相独立的发布方。同一家机构的三个页面不算交叉验证。
- 课程自带可运行的实验材料时（比如用固定种子生成的示意数据和 SQL），可以把它登记成一个来源，`url` 写课程文件夹里的相对路径（如 `lab/queries.sql`），并在 title 或 publisher 里写明“示意数据，非真实数据”。基于它算出的数字，evidence 里写查询的节名和输出。

## 3. claims.json：边写边登记

**需要登记的说法：**
- 数字、单位、日期、版本、默认值、配置名、上下限
- 绝对说法：不支持、不能、只能、唯一、总是、从不、第一个、首次……
- 以事实口吻陈述的机制（“X 发生是因为 Y”）
- 比较（A 比 B 快、更可靠、更便宜）
- 历史与归属（谁、何时提出或发明）
- 类比的**失效处**、自测答案、复述要点、易卡壳提示。它们也在陈述事实，而且是学习者会背下来的部分。

**不需要登记的：** 类比本身、设问、教学引导语。

`page` 写说法所在页面的 id；对全课通用的事实（比如内容基线里的版本号和发布日期）写 `"course"`。长的复合说法不用拆成碎句，检查脚本能识别一条长说法覆盖了页面上的哪几个分句。

**字段：**

```json
{"id": "C12", "page": "05-producer", "kind": "default",
 "text": "linger.ms 默认 5ms（4.0 起，此前为 0）",
 "version_sensitive": true, "sources": ["S3"],
 "url": "https://kafka.apache.org/41/configuration/producer-configs/",
 "evidence": "linger.ms … Default: 5",
 "status": "draft", "note": ""}
```

- `kind`：number、default、version、negative、mechanism、comparison、history、definition、computed、rule 之一。
- `text`：按页面上的写法转述，**数字要原样保留**，检查脚本会拿它和页面上的数字比对。
- `evidence`：来源里支持这条说法的原文，逐字引用，40 词以内。如果是计算得出的，就写算式和结果。
- 计算类说法：用 python 实际算一遍，把算式写进 evidence，不要心算。

## 4. 核查轮

等所有页面写完后，**单独做一轮**，目标是证伪每一条，而不是确认。

**核查每一条的方法：**
- **按来源分批，而不是按条目。** 把台账按 url/sources 分组，每个来源只打开一次，一次核完所有引用它的条目。一门课常有 150–250 条说法，逐条去抓网页既慢又贵。
- 找到支持这条说法的原句，逐字抄进 evidence。
- 版本敏感的说法，来源必须对应基线版本。
- 绝对否定需要明确的证据。“我没找到这个功能”不算证据：先用功能名去搜 release notes、改进提案（KIP、PEP、RFC 等）和 changelog，确认它在基线版本里确实不存在，再下“不支持”的结论。
- 优先核查风险最高的几类：default、version、negative、number，以及实战页和自测答案里的说法。学习者会照着这些去做。

**数字要读原始资料，不要信摘要。** WebFetch 这类工具是用一个小模型对网页做摘要后再回答的，数字、日期、版本号可能被它说错。凡是数字，都要用 curl 取原始 HTML、CSV 或数据接口（统计局、央行、FRED、官方文档表格等），在原文里找到那个数，再抄进 evidence。二手报道里的数字也会错：同一个数至少对照一手来源。某个网站拒绝抓取时，换同一数据的一手发布方或官方数据接口，不要退回二手文章。

**四种结论：**
- `verified`：原样成立。
- `corrected`：页面和 text 都改成正确版本，note 里写“原稿写 X，按 S3 改为 Y”。
- `softened`：找不到可靠依据，就把说法改到有依据的程度，比如“通常”“多数实现中”“截至 X 版文档”，或者去掉具体数字。
- `removed`：从页面上删掉。

不允许留下 `draft`，检查脚本会直接报错。

**并行核查（能派子 agent 时推荐）：**
1. 把台账按来源或页面切成若干批，每批约 40–60 条，交给**没参与写作**的核查 agent。给每个核查者：它负责的 claim id 列表、`claims.json`、`sources.json`、相关页面片段的路径，以及本文件。
2. 给核查者的任务说明可以这样写：“逐条尝试证明这些说法是错的或已过时；找不到反证时，再到来源里找支持它的原句。把结论写进 `_work/verify/<你的批次名>.json`，不要直接改 claims.json 或页面。”
3. 结论文件的格式见 `scripts/merge_verdicts.py` 顶部说明。每条写 id、status、url、evidence；修正或弱化的条目写新的 text，以及对页面的精确替换 `edits: [{page, old, new}]`。核查中发现的未登记说法，用 `"id": "new"` 追加。
4. 全部核查者完成后运行 `python3 <skill-dir>/scripts/merge_verdicts.py <course>`。它会回写台账、应用页面改动，并列出找不到原文的改动，这些手动处理。
5. 没有子 agent 时，自己做同样的事：先把写作的思路放下，换成“这条可能是错的”的视角，按来源分批核查。

## 5. 改一处，改全部

同一个事实通常出现在好几处：要点、类比边界、深入层、自测答案、靶心实战、验收页的复述要点和易卡壳提示。任何一条被修正后，用旧的措辞或数字 grep 全部片段，每一处都改掉。验收页的类比库是构建脚本从各概念页自动收集的，会跟着更新。

## 6. 对学习者坦白

- 每页的“本页来源”、地图页的来源清单和内容基线、验收页的“事实核查说明”都由构建脚本根据 sources.json 和 claims.json 自动生成。你只需要把数据记准。
- 重要但无法核实的点，在页面上直说，比如“各厂商实现不一，以官方文档为准”，不要猜一个数。
